REST 01 / 10 · The Idea
What is a REST API?
Nouns in the URL, verbs in the method, data as JSON

An API (Application Programming Interface) is a menu of things one program lets another program ask for. A web API serves that menu over HTTP, the same protocol your browser uses for web pages. REST (REpresentational State Transfer) is a set of conventions for designing that menu so that every API looks familiar. It works like a restaurant:

📦

Resources are nouns

Everything the API manages is a resource with its own URL. A whole collection is /messages. One item is /messages/7. One user's avatar is /users/3/avatar. URLs name things, never actions: there is no /deleteMessage.

⚙️

Methods are verbs

What to do with the thing goes in the HTTP method. GET /messages/7 reads it, PATCH /messages/7 edits it, DELETE /messages/7 removes it. The URL stays the same and only the verb changes.

🧾

Data travels as JSON

Request bodies and responses are JSON text, so a JavaScript page, a Python script and a phone app can all read them. FastAPI converts your Python objects to and from JSON automatically.

🔁

Stateless

The server keeps no memory of earlier requests. Every request carries everything needed to answer it, so after login the client sends its token with every call (Authorization: Bearer …).

💡 Why AI engineers care. This is how a model leaves the notebook. Project 03 wraps the CNN in a FastAPI endpoint: the phone sends POST /predict with a photo, and the server replies with {"label": "happy", "p": 0.94}. The same pattern lets your code call ChatGPT, Claude or any other model service.
REST 02 / 10 · The Verbs
The HTTP methods
Seven verbs, one URL scheme: create, read, update, delete and two helpers
methodwhat it meansbody?safe / idempotentin the chat app
GETRead. Never changes anything.no✔ / ✔GET /messages
POSTCreate a new item in a collection. The server picks the id.yes✘ / ✘POST /messages
PUTReplace an item completely with the body you send.yes✘ / ✔PUT /users/3
PATCHChange only the fields you send.yes✘ / ✘*PATCH /messages/7
DELETERemove the item.no✘ / ✔DELETE /messages/7
HEADSame as GET, but returns only the status and headers. "Does it exist?"no✔ / ✔HEAD /users/3
OPTIONS"Which methods may I use here?" Browsers send it automatically before cross-site calls (CORS preflight).no✔ / ✔not routed (see note)

Safe means it changes nothing on the server. Idempotent means sending it once or ten times leaves the server in the same state. That's why a browser can retry a failed GET freely but warns you before re-sending a form (a POST): a second POST creates a second message. *PATCH can be idempotent ("set content to X" is), but HTTP doesn't promise it.

REST 03 / 10 · The Answer
Status codes
Three digits that tell the client what happened, before it reads the body

Every response begins with a number. The first digit is the family. The client can branch on it without understanding the body at all. The frontend's api() helper does exactly that: if (!res.ok) means "not 2xx".

2xx · success

200 OK: here's what you asked for
201 Created: POST /users, POST /messages
204 No Content: done, nothing to return (DELETE, logout)

3xx · look elsewhere

307 Redirect: a preset avatar redirects to its Unsplash photo
304 Not Modified: "your cached avatar is still good" (via ETag)

4xx · your fault

401: no token / wrong password
403: logged in, but not yours
404: no such message / user
409 Conflict: that name is taken
413: avatar over 500 KB
422: body failed validation

5xx · server's fault

500: an unhandled exception in your code
You never return this on purpose. If a client sees it, there is a bug to fix.
🔐 401 vs 403 is the pair students mix up. 401 Unauthorized really means unauthenticated: "I don't know who you are" (missing or expired token). 403 Forbidden means "I know exactly who you are, and you can't do that", for example editing someone else's message.
python: how the app sends an error
if msg.user_id != me["id"]:
    raise HTTPException(status_code=403, detail="You can only change your own messages")

FastAPI turns that exception into the response 403 with body {"detail": "You can only change your own messages"}. The frontend shows detail in a SweetAlert popup.

REST 04 / 10 · The Framework
FastAPI
Write a typed Python function; FastAPI does the HTTP plumbing around it
pip install fastapi uvicorn Python type hints → validation + docs

FastAPI is a Python framework for building APIs. You write ordinary functions and put a decorator above each one that says which method + path it answers. Here is a complete, runnable API:

python: main.py, the smallest useful FastAPI app
from fastapi import FastAPI, HTTPException
from pydantic import BaseModel, Field

app = FastAPI(title="Messages API")          # the application object
db = {}                                      # stand-in for a real database

class MessageCreate(BaseModel):              # the shape of the request body
    content: str = Field(..., min_length=1, max_length=2000)

@app.get("/messages")                        # GET /messages
def list_messages():
    return list(db.values())                 # list/dict → JSON automatically

@app.get("/messages/{message_id}")           # {message_id} is a path parameter
def get_message(message_id: int):            # "7" in the URL → int 7
    if message_id not in db:
        raise HTTPException(status_code=404, detail="Message not found")
    return db[message_id]

@app.post("/messages", status_code=201)
def create_message(msg: MessageCreate):      # a BaseModel param = the JSON body
    new_id = len(db) + 1
    db[new_id] = {"id": new_id, "content": msg.content}
    return db[new_id]

Each type hint does real work. message_id: int converts and checks the URL piece. msg: MessageCreate tells FastAPI to read the JSON body and validate it with Pydantic. A query parameter is any other plain argument, such as limit: int = 100 → /messages?limit=20. Below are the steps FastAPI runs for POST /messages in the class app:

Live Demo: what FastAPI does before and after your function
STEP 1Match the routePOST + /messages → create_message
STEP 2Run dependenciesDepends(current_user) reads Authorization
STEP 3Validate the bodyJSON → MessageCreate (Pydantic)
STEP 4Call your functionINSERT INTO messages …
STEP 5Serialize the resultresponse_model=Message → JSON

      

      
✅ You wrote none of the error handling for steps 1–3. The 422 message, with the exact field and rule that failed, is generated by FastAPI from Field(..., min_length=1). Your function only runs once the input is known to be correct.

      
🧩 Depends is FastAPI's way to say "run this first and give me the result". me: dict = Depends(current_user) on an endpoint means "this endpoint needs a logged-in user". If current_user raises 401, your function never runs.

      

        
        

        
      

    


    
    

      

        
        

          
REST 05 / 10 · The Server

          
Uvicorn

          
FastAPI is the kitchen. Uvicorn is the front door that is always open.

        

      

      
A FastAPI app is just a Python object, and it can't listen to the network by itself. Uvicorn is an ASGI server. It opens a port, accepts TCP connections, parses the raw HTTP text into a request object, calls your app, and writes the response back onto the wire. One command starts it:

      

        
terminal, in the project folder

        
uvicorn main:app --reload

      

      

        
      

      

        
      

      

        
what you see when it starts

        
INFO:     Will watch for changes in these directories: ['…/18.10.2026']
INFO:     Uvicorn running on http://127.0.0.1:8000 (Press CTRL+C to quit)
INFO:     Started reloader process [12345] using StatReload
INFO:     Application startup complete.
INFO:     127.0.0.1:52341 - "GET /messages?limit=200 HTTP/1.1" 200 OK

      

      
⚠️ Error loading ASGI app. Could not import module "main" means you ran the command from the wrong folder. Uvicorn looks for main.py in the current directory. --reload is for development only; a production server runs without it.

      
🔤 WSGI vs ASGI. Older Python servers (WSGI, used by Flask and classic Django) handle one request per worker at a time. ASGI is the async successor: one Uvicorn process can wait on many slow clients at once. That's the "Fast" in FastAPI.

REST 09 / 10 · Storage

          
The database behind it

          
Each resource is a table, each request is one or two SQL statements

        

      

      
The app stores everything in SQLite: a whole database in one file (messages.db), built into Python as import sqlite3, with no server to install. When Uvicorn starts, init_db() runs CREATE TABLE IF NOT EXISTS for three tables:

      

        
      

      
The REST layer is a thin translation. Each method on a resource becomes one SQL statement on its table:

      

        
HTTPSQLCRUD

        
          
POST /messagesINSERT INTO messages (user_id, sender, content, …) VALUES (?, ?, ?, …)Create

          
GET /messagesSELECT * FROM messages ORDER BY id DESC LIMIT ? OFFSET ?Read

          
GET /messages/7SELECT * FROM messages WHERE id = ?Read

          
PATCH /messages/7UPDATE messages SET content = ?, updated_at = ? WHERE id = ?Update

          
DELETE /messages/7DELETE FROM messages WHERE id = ?Delete

        
      

      
How login works, using the sessions table:

      

        
1 · POST /login
Find the user by name. Hash the typed password with the stored salt and compare it to password_hash. The plain password is never stored.

        
2 · new session row
token = secrets.token_urlsafe(32) → INSERT INTO sessions. The token goes back to the browser.

        
3 · every later request
Authorization: Bearer <token> → current_user runs sessions JOIN users to find who you are.

        
4 · POST /logout
DELETE FROM sessions WHERE token = ?. From then on that token gets a 401.

      

      
🛡️ Always ?, never f-strings with user input. Every query passes values as parameters: execute("… WHERE id = ?", (message_id,)). SQLite inserts them safely, so a message containing '; DROP TABLE users; -- is stored as harmless text. Building SQL with f"... {name}" would be an SQL injection hole.

      
🧬 The schema grew while the app was being written. messages first had only a sender name. Accounts came later, so init_db() checks PRAGMA table_info and runs ALTER TABLE … ADD COLUMN user_id on old databases. You can still see this in the class database: message #3 has user_id = NULL because it was posted before users existed.

What makes it fail
"Make me a chat app" in one go. You get a pile of code you can't test in pieces, can't explain, and can't fix when step 3 breaks step 1. Vibe coding still needs you to read the code, which is what Lesson 03 is for.
