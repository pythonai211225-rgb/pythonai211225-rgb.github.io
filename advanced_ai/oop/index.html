OOP 01 / 08 · The Idea
What is OOP?
Keep the data and the actions on it together, in one object

Think of a real phone. It has things: a colour, a model, a battery level. It does things: turns on, charges, makes calls. Object-oriented programming (OOP) writes code the same way. Each object holds its own data (called attributes) and the actions that work on that data (called methods).

The same two phones, written two ways
📐

Class

The blueprint: what every phone has and can do. Written once: class MobilePhone:

📱

Object (instance)

One real phone built from the blueprint, with its own values: phone1 = MobilePhone(...)

🏷️

Attribute

A value the object has: phone1.color, phone1.battery

⚙️

Method

A function the object does, written inside the class: phone1.charge(20)

💡 Everything in Python is already an object. type(5) is <class 'int'>, and "hi".upper() calls the method upper of a str object. Writing your own class just adds new kinds of objects to the language.
OOP 02 / 08 · History
The first OOP languages
An idea from 1960s Norway that now runs most of the software you use

OOP began with a practical problem. Two Norwegian scientists wanted to simulate real systems, such as ships in a harbour or customers in a queue. They found it natural to describe each thing as a separate "object" with its own data and behaviour. Click a point on the timeline:

Timeline: click a language
🏆 Two Turing Awards. Ole-Johan Dahl and Kristen Nygaard received the Turing Award (the "Nobel prize of computing") in 2001 for the ideas behind OOP in Simula. Alan Kay received it in 2003, partly for Smalltalk. Kay is also the person who coined the term "object-oriented".

OOP 04 / 08 · The Benefits
Why OOP is good
Big programs stay understandable when each part looks after itself

✅ What OOP gives you

  1. Code that looks like the world. A phone, a user, a message: one class each. It is easy to say what goes where.
  2. Each object protects its own data. Only the battery's own methods change the battery, so it can never reach 120%.
  3. Reuse. Write MobilePhone once and create a thousand phones. Extend it with SmartPhone without copying code.
  4. Teamwork. One student writes User, another writes Message. They only need to agree on the methods.
  5. Easier to change and test. A bug in charging lives in one method of one class.

🧩 You already use it

  • model = Sequential(): the Keras model is an object. model.fit() and model.predict() are its methods.
  • df = pd.read_csv(...): a DataFrame object. df.head() is a method, df.shape an attribute.
  • app = FastAPI(): the REST API is an object, and @app.get calls its method.
  • "hello".upper(), [3, 1].sort(): strings and lists are objects too.
🧠 The real reason: big programs. A 50-line script fits in your head. A 50,000-line app does not. OOP lets you think about one class at a time and trust the others to do their own job.
OOP 05 / 08 · The Limits
When OOP is not recommended
A class is a tool, not a rule

⚠️ Prefer something simpler when…

  1. The program is small. A 20-line script that reads a file and prints an average needs functions, not classes. Talk title from PyCon 2012: "Stop Writing Classes". If a class has only __init__ and one method, it should probably be a function.
  2. You are crunching numbers. Machine learning works on arrays. One CNN photo is 64×64×3 = 12,288 numbers. Each Python float object takes 24 bytes; inside a NumPy array a number takes 8, and NumPy runs the maths in fast C. A Pixel class per number would be far slower.
  3. Data flows through steps. Load → clean → transform → save reads best as a chain of functions, or a pandas pipeline.
  4. The class tree gets deep. Device → Phone → SmartPhone → GamingPhone → … A change at the top breaks things far below. The well-known advice is: "favour composition over inheritance". Give a phone a Battery object instead of inheriting from a battery class.
  5. Many threads share one object. Objects that change can be changed by two threads at once, which causes hard bugs. Data that never changes is safer there.

✅ OOP fits well when…

  • there are many things of the same kind (users, phones, messages, game characters)
  • each thing has a state that changes over time (battery, score, is_on)
  • the program is big, lives a long time, or is written by a team
  • you build a library for others (Keras, pandas, FastAPI)
python: a class that should be a function
# too much ceremony for one calculation
class AverageCalculator:
    def __init__(self, numbers):
        self.numbers = numbers

    def calculate(self):
        return sum(self.numbers) / len(self.numbers)

print(AverageCalculator([80, 90, 100]).calculate())   # 90.0

# the same thing, simpler
def average(numbers):
    return sum(numbers) / len(numbers)

print(average([80, 90, 100]))                         # 90.0
