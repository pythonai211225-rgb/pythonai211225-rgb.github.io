TOPICS 2 · 01 / 10 · Encoding
get_dummies & OneHotEncoder
A model cannot subtract Teacher from Developer — so give it switches instead
pd.get_dummies(X, columns=[...], dtype=int) → one 0/1 column per category

Here is the notebook's table. Two of its columns are text, and every model you have met so far only accepts numbers:

agejobcitysalary
25DeveloperTel Aviv15000
32TeacherHaifa12000
45DeveloperJerusalem22000
29DoctorHaifa18000
38TeacherTel Aviv16000

The tempting shortcut is to number the categories — Developer = 0, Teacher = 1, Doctor = 2. Do that and you have quietly told the model that a Doctor is twice a Teacher, and that a Teacher sits exactly halfway between a Doctor and a Developer. None of that is true, and a distance-based model will believe every word of it.

One-hot encoding refuses to make up an order. Each category becomes its own column holding a single switch: 1 if this row is that category, 0 otherwise. Every row has exactly one 1 per original column, which is where the name comes from.

Live Demo — watch the two text columns fan out into switches
python — the notebook cell
import pandas as pd

df = pd.DataFrame({
    'age': [25, 32, 45, 29, 38],
    'job': ['Developer', 'Teacher', 'Developer', 'Doctor', 'Teacher'],
    'city': ['Tel Aviv', 'Haifa', 'Jerusalem', 'Haifa', 'Tel Aviv'],
    'salary': [15000, 12000, 22000, 18000, 16000]
})

X = df.drop(columns=['salary'])
y = df['salary']

X = pd.get_dummies(
    X,
    columns=['job', 'city'],
    dtype=int          # without this you get True/False
)

X
📐 What the shape tells you. The frame goes from 3 feature columns to 7: age survives untouched, job becomes 3 columns and city becomes 3. The rule is simple — every categorical column is replaced by as many columns as it has distinct values. A postcode column with 400 values becomes 400 columns, which is exactly when one-hot stops being a good idea.
⚠️ drop_first=True and the dummy trap. The three job columns always sum to 1, so any one of them is perfectly predictable from the other two. For a linear model that is collinearity — the coefficients become unstable and cannot be read individually. Dropping one category fixes it and loses nothing: "not Doctor and not Teacher" already means Developer. For trees, forests and KNN it does not matter, and dropping a column only makes the encoding harder to read.

✓ pd.get_dummies

  1. One line, keeps a DataFrame with readable column names.
  2. Perfect for exploring a table in a notebook.
  3. Handles several columns at once via columns=[...].

✗ but it cannot be fitted

  1. It has no memory. Call it on new data and you get whatever categories that data happens to contain.
  2. A category missing at prediction time silently produces a narrower frame — and the model refuses to predict.
  3. It cannot live inside a Pipeline, so it cannot be part of cross-validation.

OneHotEncoder is the same idea built as a proper transformer: it learns the list of categories in fit and reproduces exactly those columns, in the same order, every time transform is called. That is the version panel 03 puts inside the pipeline.

TOPICS 2 · 02 / 10 · Composition
Pipeline
One object that is the whole recipe, not just the last step
Pipeline([('scaler', MinMaxScaler()), ('knn', KNeighborsClassifier())]) → an estimator

A Pipeline is a list of named steps. Every step except the last must be a transformer — an object with fit and transform. The last step is the estimator, the thing that actually predicts. The pipeline then behaves like a single model:

🏋

pipe.fit(X, y)

Walks the steps in order. Each transformer gets fit_transform — it learns its statistics from what arrives, then passes the transformed data on. The last step gets a plain fit.

🔮

pipe.predict(X)

Walks the same steps, but every transformer now only gets transform — it reuses the statistics it learned during fit. Nothing is re-learned from the data you are predicting.

That single difference — fit_transform on the way in, transform on the way out — is the entire reason pipelines exist. It is the rule from the previous deck, enforced by the object instead of by your memory.

Live Demo — a row travelling through Pipeline([('scaler', MinMaxScaler()), ('knn', KNeighborsClassifier(3))])
python — the notebook cell
from sklearn.neighbors import KNeighborsClassifier
from sklearn.preprocessing import MinMaxScaler
from sklearn.pipeline import Pipeline

pipeline = Pipeline([
    ('scaler', MinMaxScaler()),
    ('knn', KNeighborsClassifier(n_neighbors=3))
])

pipeline.fit(X, y)

# raw values in — the pipeline scales them itself
pipeline.predict([[225, 7, 150]])
🏷 The names are not decoration. 'scaler' and 'knn' are how you reach into the pipeline later: pipeline.named_steps['knn'] gives you the classifier, and 'knn__n_neighbors' is how a grid search addresses its parameters. Appendix A2 covers the naming rules. If you do not care about the names, make_pipeline(MinMaxScaler(), KNeighborsClassifier()) invents them for you — lowercased class names, so 'minmaxscaler' and 'kneighborsclassifier'.
🧷 Why this matters beyond tidiness. Without a pipeline the scaler and the model are two variables that must be kept in sync by hand — in cross-validation, in the grid search, in the file you save, and in the service that loads it. Every one of those is a place where they can drift apart. A pipeline makes that impossible by construction, which is the subject of the next three panels.
TOPICS 2 · 03 / 10 · The Question
Encoder in the pipeline
Is it actually a better idea than get_dummies up front?
✓

Short answer: yes, once the model leaves the notebook.

For a quick look at a table, pd.get_dummies is faster to type and easier to read, and nothing bad happens. The moment there is a second batch of data — a test set, a fold, a row arriving from production — get_dummies has no memory of what the first batch looked like, and the columns stop lining up.

An encoder inside a pipeline remembers. That is the whole difference, and it is not a style preference.

A pipeline needs one input and one output per step, but a real table has two kinds of column: numbers that want scaling and text that wants encoding. ColumnTransformer is the fork in the pipe — it sends each group of columns down its own branch and glues the results back together side by side:

Live Demo — one table, two branches, one matrix

Switch the demo to the second setting and the difference becomes concrete. A row arrives whose city is Eilat, a value the model has never seen:

✗ get_dummies on the new row

  1. It builds columns from this row's categories, so it produces city_Eilat and no city_Haifa, city_Jerusalem or city_Tel Aviv.
  2. The frame now has 3 columns where the model expects 7.
  3. predict raises ValueError: The feature names should match those that were passed during fit, then lists city_Eilat as unseen and five columns as missing. Fitted on a bare numpy array instead, sklearn can only count: X has 3 features, but LinearRegression is expecting 7 features as input.
  4. And that is the good case. Line the columns up by hand in the wrong order and it predicts confidently and wrongly instead.

✓ OneHotEncoder(handle_unknown='ignore')

  1. It learned the category list during fit and always emits those same 7 columns, in that same order.
  2. An unseen category becomes a row of zeros in the city block — "none of the cities I know".
  3. predict works. The prediction leans entirely on the other features, which is the honest answer for a city the model has never seen.
python — the shape to remember
from sklearn.compose import ColumnTransformer
from sklearn.preprocessing import OneHotEncoder, StandardScaler
from sklearn.pipeline import Pipeline
from sklearn.linear_model import LinearRegression

# X still has its text columns — no get_dummies anywhere
X = df.drop(columns=['salary'])
y = df['salary']

prep = ColumnTransformer([
    ('num', StandardScaler(), ['age']),
    ('cat', OneHotEncoder(handle_unknown='ignore'), ['job', 'city'])
])

model = Pipeline([
    ('prep', prep),
    ('reg', LinearRegression())
])

model.fit(X, y)

# raw text goes straight in — the pipeline encodes it
new = pd.DataFrame([{'age': 31, 'job': 'Teacher', 'city': 'Eilat'}])
model.predict(new)
🔎 Reading the encoded columns back. model.named_steps['prep'].get_feature_names_out() returns ['num__age', 'cat__job_Developer', ...] — the same names get_dummies would have given you, prefixed by the branch. You need them the moment you want to look at coef_, because after a ColumnTransformer the coefficient order is no longer the order of your original columns.
!

The honest caveats

It is more to type. Three imports and a nested object instead of one function call. On a five-row exploration that is not worth it.

You lose the DataFrame. The output is a numpy array (or a sparse matrix — pass sparse_output=False if you want to look at it), so .head() no longer tells you anything without get_feature_names_out().

Column selection is by name, so the input must stay a DataFrame. Hand the fitted pipeline a bare numpy array at predict time and it will not find 'job'.

The rule of thumb: get_dummies while you are looking at the data, ColumnTransformer the moment you write cross_val_score, GridSearchCV or joblib.dump.

TOPICS 2 · 04 / 10 · Honest Scoring
cross_val_score + pipeline
A brand new scaler for every fold, fitted on that fold's training rows only
cross_val_score(pipeline, X, y, cv=3, scoring='accuracy') → array of 3 scores

Hand cross_val_score a bare model and you have to scale the data yourself first — which means scaling it once, using the minimum and maximum of every row, including the rows that are about to become test data in each fold. The test set has then had a say in its own scaling. Hand it a pipeline instead and sklearn clones the whole pipeline for each fold, so the scaler is fitted on the training rows of that fold and nothing else.

split

Fold k's test rows are set aside. They are not visible to anything that follows.

fit_transform

A fresh MinMaxScaler learns min and max from the training rows of this fold.

transform

The test rows are scaled with those same training statistics — they may land outside [0, 1], and that is correct.

score

Predict the test rows, write down the accuracy, throw the whole pipeline away, repeat.

Live Demo — the notebook's 9 fruits, cv=3, MinMax + KNN(3). Green = test rows of that fold.
python — the notebook cell
from sklearn.model_selection import cross_val_score
from sklearn.pipeline import Pipeline

pipeline = Pipeline([
    ('scaler', MinMaxScaler()),
    ('knn', KNeighborsClassifier(n_neighbors=3))
])

scores = cross_val_score(
    pipeline,
    X, y,
    cv=3,
    scoring='accuracy'
)

print("Scores:", scores)
print(f"Average Accuracy: {scores.mean():.2f}")

# Scores: [0.66666667 1.         0.66666667]
# Average Accuracy: 0.78
🔎 Be honest about this dataset. Flip the demo to "once, before the split" and the three fold scores do not move — on 9 rows the min and max of each column barely change when you remove 3 of them. The leak is real but too small to see here. That is exactly why the habit matters: the bug does not announce itself on toy data, it announces itself on the day a single extreme row lands in a test fold and takes the scaling with it. What does change is the fold statistics shown in the demo — fold 3 learns weight: 120…170 where the global scaler saw 115…180.
⚠️ cv=3 is not plain KFold. When the estimator is a classifier, sklearn quietly uses StratifiedKFold, so every fold keeps one apple, one orange and one banana. On this deliberately sorted fruit table that is the difference between working folds and folds that test a class the model never trained on. For a regressor — panel 07 — it really is plain KFold, in row order, which has consequences of its own.
TOPICS 2 · 05 / 10 · Hyper-parameters
GridSearchCV
Stop guessing k. Try them all, cross-validate every one, keep the winner
GridSearchCV(estimator, param_grid, cv=3, scoring='accuracy') → .best_params_ · .best_score_ · .best_estimator_

A parameter is something the model learns from the data — the coefficients of a regression, the split points of a tree. A hyper-parameter is something you choose before it ever sees the data: n_neighbors, C, max_depth, the polynomial degree. Nothing in fit touches them, so the only way to choose one is to try it and measure.

GridSearchCV is that loop written down. Give it a dictionary of lists, and it takes the Cartesian product — every combination of every value — and runs a full cross-validation on each one:

$$\text{fits} = \underbrace{|C| \times |\gamma| \times |\text{kernel}|}_{\text{combinations}} \times \underbrace{\text{cv}}_{\text{folds}} \;+\; \underbrace{1}_{\text{refit on all data}}$$

For the notebook's SVM grid that is 4 × 4 × 4 = 64 combinations, each cross-validated 3 times, so 193 model fits from one call. This is why n_jobs=-1 exists, and why a careless third list in the dictionary can turn a 10-second search into a coffee break.

Live Demo — a grid being searched, cell by cell. 18 fruits, cv=3, MinMax + KNN.
python — the notebook's SVM search (with the typo fixed)
from sklearn.svm import SVC
from sklearn.preprocessing import StandardScaler
from sklearn.pipeline import Pipeline
from sklearn.model_selection import GridSearchCV

pipeline = Pipeline([
    ('scaler', StandardScaler()),
    ('svm', SVC())
])

param_grid = {
    'svm__C':      [0.1, 1, 10, 100],
    'svm__gamma':  [0.01, 0.1, 1, 10],
    'svm__kernel': ['linear', 'rbf', 'poly', 'sigmoid']
}

grid = GridSearchCV(
    pipeline,
    param_grid,
    cv=3,
    scoring='accuracy',
    n_jobs=-1          # n_jobs, not njobs — see appendix A1
)

grid.fit(X, y)

print(grid.best_params_)   # {'svm__C': 0.1, 'svm__gamma': 0.01, 'svm__kernel': 'linear'}
print(grid.best_score_)    # 1.0
⚠️ That result is a warning, not a triumph. On those 24 points, 54 of the 64 combinations score a perfect 1.0 and the worst still manages 0.875. The two classes are separated by a wide empty corridor, so almost any setting draws a line through it. best_params_ reports C=0.1, gamma=0.01, linear only because sklearn walks the grid in sorted order and keeps the first maximum. Change the order of the lists and you get a different "best". When the top of the grid is a plateau, the honest reading is "this choice does not matter here" — look at cv_results_ before you believe a winner.
📊 What comes back. best_params_ is the winning dictionary, best_score_ is its mean CV score, and best_estimator_ is the whole pipeline refitted on all the data with those parameters — ready to predict, ready to save. cv_results_ is the full table: one row per combination, with the score of every individual fold, the mean, the standard deviation and the rank. Load it with pd.DataFrame(grid.cv_results_) and sort by rank_test_score.
🧩 Search the pipeline, not the model. Passing the pipeline rather than the bare SVC means the scaler is re-fitted inside every one of those 192 folds. Pass a pre-scaled X and a bare model, and the search is choosing hyper-parameters against scores that have already been inflated by the leak. Panel 04 is the reason; this is where it pays.
TOPICS 2 · 06 / 10 · Scoring
neg_mean_squared_error
Why sklearn hands you a negative number and expects you to be pleased

Grid search does one thing with the numbers it collects: it takes the maximum. That works for accuracy, where bigger is better. It is exactly wrong for an error, where bigger is worse. Rather than teach the search which metrics point which way, sklearn made every scorer point the same way by flipping the sign of the ones that do not:

$$\texttt{neg\_mean\_squared\_error} = -\,\frac{1}{n}\sum_{i=1}^{n}\left(y_i - \hat{y}_i\right)^2$$

An MSE of 0.72 is reported as −0.72, an MSE of 264 as −264. The best model is now the one with the biggest score, because −0.72 is far to the right of −264 on the number line. The rule across the whole library: greater is always better, and any metric whose name starts with neg_ is an error wearing a minus sign.

Live Demo — the same eight degrees, before and after the sign flip
python — remember the minus when you print
grid = GridSearchCV(model, param_grid, cv=5,
                    scoring='neg_mean_squared_error')
grid.fit(X, y)

print(grid.best_score_)        # -0.7153780577554179
print(-grid.best_score_)       # 0.7153780577554179  <- the actual MSE

# and for a number you can read in the units of y:
np.sqrt(-grid.best_score_)     # 0.8458  -> RMSE, same units as y

# the whole grid, error side up
pd.DataFrame({
    'degree': grid.cv_results_['param_poly__degree'],
    'mse': -grid.cv_results_['mean_test_score']
})
📐 The other regression scorers. 'neg_mean_absolute_error' punishes a big miss proportionally rather than quadratically, so it is the one to reach for when outliers should not dominate. 'neg_root_mean_squared_error' is the square root of MSE, in the units of y. 'r2' is the odd one out — it is genuinely "bigger is better" already, so it carries no neg_ prefix, and it is the default when you pass no scoring at all to a regressor. That default is worth knowing: leave scoring off and you are optimising R², not MSE.
⚠️ The mistake this prevents. Print best_score_ for a regression, see -0.715, and it is very easy to read it as "a terrible model" or to write abs(...) everywhere out of habit. It is one number, already correct, already the mean over the folds. Negate it once, when you report it.
TOPICS 2 · 07 / 10 · Model Selection
Searching for the degree
PolynomialFeatures has a hyper-parameter too — so let the grid pick it
param_grid = {'poly__degree': range(1, 9)} → best degree = 3

Polynomial regression is a pipeline in disguise: PolynomialFeatures expands x into [1, x, x², …, x^d], and a plain LinearRegression fits a straight line through those new columns. The degree d is not learned — it is chosen. Which makes it exactly the kind of thing a grid search is for.

Live Demo — the notebook's 30 points, fitted at every degree the grid tries
3
1 the fit at this degree
2 cross-validated MSE per degree
python — the notebook cell, completed
from sklearn.preprocessing import PolynomialFeatures
from sklearn.linear_model import LinearRegression
from sklearn.pipeline import Pipeline
from sklearn.model_selection import GridSearchCV

model = Pipeline([
    ('poly', PolynomialFeatures()),
    ('regression', LinearRegression())
])

param_grid = {'poly__degree': range(1, 9)}

grid = GridSearchCV(model, param_grid, cv=5,
                    scoring='neg_mean_squared_error')
grid.fit(X, y)

print("Best degree:", grid.best_params_['poly__degree'])   # 3
print("Best MSE:", -grid.best_score_)                    # 0.7154

# the notebook's plot needs these two lists, which the cell
# never built — pull them out of cv_results_ instead:
degrees = list(param_grid['poly__degree'])
errors  = -grid.cv_results_['mean_test_score']

plt.plot(degrees, errors, marker='o')
plt.yscale('log')          # 11773 and 0.72 on one axis
plt.xlabel("Polynomial Degree")
plt.ylabel("Cross-Validation MSE")
plt.show()
📐 Read the curve, not just the winner. Degree 1 is hopeless (MSE 11 773) — a straight line through data that clearly bends. Degree 2 gets within 263. Degree 3 lands on 0.72, a factor of 360 better again. And then it gets worse: 14.6 at degree 4, 122 at degree 5, 464 at degree 7. That U shape is the whole story of model selection — the left arm is underfitting, the right arm is overfitting, and cross-validation is what makes the right arm visible at all.
⚠️ Watch what happens at degree 8. The fit on the left still looks flawless — but x⁸ at x = 30 is 6.5 × 10¹¹, so the design matrix columns differ by twelve orders of magnitude and the fit becomes numerically fragile. On this page the browser's QR solver and sklearn's SVD solver agree to four decimals for degrees 1–7 and then disagree loudly at 8 (127.7 vs 684.9) — both enormous, both correct in the only sense that matters. If you need high degrees, scale x first: Pipeline([('scale', StandardScaler()), ('poly', PolynomialFeatures()), ('reg', LinearRegression())]).
🔎 And note which folds you are getting. The estimator is a regressor, so cv=5 is plain KFold with no shuffling: fold 1 is x = 1…6, fold 5 is x = 25…30. Every fold is therefore an extrapolation test — the model must predict a stretch of x it never saw. That is brutal, and it is why the high degrees blow up so spectacularly. It is also, for data that arrives in order, the realistic question.
TOPICS 2 · 08 / 10 · The Bend
The elbow for the degree
When the curve only ever improves, the answer is the bend, not the minimum

Cross-validated error has a genuine minimum — that is what made panel 07 easy. Training error does not. Add a degree and the polynomial can only fit the points it has already seen better or equally well, so the curve slides downwards forever. There is no argmin worth taking: it would always hand you the largest degree in the list.

This is the same shape as K-Means inertia, and it takes the same answer: find the elbow — the degree after which each extra parameter buys you almost nothing.

Live Demo — training MSE per degree, with the sweet spot found and circled

The method the animation is running is the standard one, and it is worth being able to do by hand:

draw the chord

A straight line from the first point of the curve to the last. It is what "no bend at all" would look like.

measure the gap

For every degree, how far does the real curve sit below that chord?

take the largest

The point that hangs furthest below the chord is the elbow. That is all kneed does, formalised.

sanity-check it

Compare against the cross-validated answer. If they disagree, trust cross-validation — it is measuring the thing you actually care about.

python — training error per degree, and the elbow
import numpy as np
import matplotlib.pyplot as plt
from sklearn.metrics import mean_squared_error

degrees, errors = list(range(1, 9)), []

for d in degrees:
    m = Pipeline([('poly', PolynomialFeatures(degree=d)),
                  ('regression', LinearRegression())])
    m.fit(X, y)
    errors.append(mean_squared_error(y, m.predict(X)))

# errors: 3139.08, 26.22, 0.4415, 0.4064, 0.3134, 0.1886, 0.1847, 0.1692
#          |         |       ^-- from here on, nothing happens

# the elbow: furthest point below the first-to-last chord.
# on a log axis, because the values span 4 orders of magnitude
v = np.log10(errors)
chord = np.linspace(v[0], v[-1], len(v))
best  = degrees[np.argmax(chord - v)]

print("elbow at degree", best)     # 3

plt.plot(degrees, errors, marker='o')
plt.yscale('log')
plt.axvline(best, ls='--', color='green')
plt.show()
✅ The two methods agree here. The elbow on training error says degree 3; the cross-validated grid search in panel 07 also says degree 3. That agreement is the reassuring case, and it is not a coincidence — the point where the training error stops improving is usually the point just before the model starts memorising noise.
⚠️ The elbow depends on the axis you draw it on. Flip the demo to a linear axis and the bend appears to be at degree 2: the drop from 3139 to 26 is so enormous that everything after it looks like a flat line at zero. On a log axis — the right choice when the values span four orders of magnitude — the same data bends at 3. Nothing about the model changed; only the picture did. Whenever an elbow decides something for you, say which scale you read it on.
🔎 When to reach for each. Use cross-validation whenever the metric can get worse — held-out error, accuracy, R². Use the elbow only when the metric is monotone by construction and there is nothing to maximise: K-Means inertia, training error, explained variance against the number of PCA components. The elbow is a judgement call dressed up as a rule, and it should be the second opinion, never the only one.
TOPICS 2 · 09 / 10 · Shipping
Saving the pipeline
Save the scaler with the model, and the loaded file scales for you
joblib.dump(grid.best_estimator_, 'model.pkl') → one file, scaler included

A fitted MinMaxScaler is not code — it is data: the min and max of every column, learned from your training set. Lose that data and the model is useless, because the numbers it was trained on no longer mean anything. Save the model alone and you have saved half of a working system.

Because a pipeline is a single estimator, joblib.dump puts both halves in one file. What comes back out takes raw, unscaled values — exactly the values your application actually has:

Live Demo — the same raw fruit, sent to both files. Really computed, both branches.
python — the notebook cell
import joblib

# best_estimator_ is the whole pipeline, refitted on all the data
best_model = grid.best_estimator_

joblib.dump(best_model, 'knn_fruit_model.pkl')

# ---- somewhere else entirely: a service, a script, next week ----

loaded_model = joblib.load('knn_fruit_model.pkl')

# IMPORTANT: raw values, NOT scaled values.
# The scaler travelled inside the file and runs first.
new_fruit = np.array([[225, 7, 150]])

print(loaded_model.predict(new_fruit))   # ['apple']
⚠️ The failure this prevents is not hypothetical. Save only the KNeighborsClassifier, feed it the same raw row [225, 7, 150], and it answers 'orange' — confidently, with no error and no warning. The 18 rows it memorised were already scaled into [0, 1]; a raw row sits hundreds of units outside that cube, so the "nearest" stored point is simply whichever one has the largest coordinates — [255, 10, 182], an orange. The model is not broken. The missing scaler is. A wrong answer that never raises is the most expensive kind of bug there is.
📦 joblib or pickle? joblib is the one sklearn recommends: same idea as pickle, but far more efficient with the large numpy arrays inside a fitted model. Both write a Python-specific format, and both have the same three caveats — never load a .pkl you did not create (loading executes code), the file is tied to the library versions that wrote it, so pin them, and it is not an archive format. For long-term storage or another language, export to ONNX or PMML instead.
🎁 The pattern, end to end. ColumnTransformer or scaler → model, wrapped in a Pipeline; the pipeline handed to GridSearchCV; best_estimator_ written out with joblib.dump; the service calls joblib.load(...).predict(raw_row) and knows nothing about scaling, encoding or degrees. Every panel in this deck is one link in that chain.

APPENDIX A1 · Debugging
Notebook gotchas
Three cells in the lesson notebook do not run — and each one teaches something

Run the notebook top to bottom and two cells stop with an exception. They are worth walking through, because each failure is a common one and the error messages are more helpful than they look.

1njobs=-1 — the missing underscore
The SVM grid search passes njobs=-1. Python has no idea what that is:
TypeError: GridSearchCV.__init__() got an unexpected keyword argument 'njobs'
The parameter is n_jobs. sklearn separates words with underscores everywhere — n_jobs, n_neighbors, n_estimators, random_state. The good news is that sklearn validates its keyword arguments strictly, so a typo raises immediately rather than being silently ignored. n_jobs=-1 means "use every core"; on 192 fits of a 24-row dataset it will not actually help much, because starting the worker processes costs more than the fits do.
2GridSearchCV used but never imported
The polynomial-degree cell imports cross_val_score at the top and then calls GridSearchCV:
NameError: name 'GridSearchCV' is not defined
Add from sklearn.model_selection import GridSearchCV. This one only bites when you run the notebook fresh — in a kernel that already ran the SVM cell, the name is still in memory and everything works. That difference between "works in my kernel" and "works from the top" is worth taking seriously: Kernel → Restart & Run All before you share a notebook.
3degrees and errors were never built
The same cell finishes by plotting two lists it never created:
NameError: name 'degrees' is not defined
Once you switch from a hand-written loop to GridSearchCV, the per-degree errors live in cv_results_ rather than in a list you appended to. Pull them back out:
python — the two missing lines
degrees = list(param_grid['poly__degree'])
errors  = -grid.cv_results_['mean_test_score']   # note the minus
🔎 One more, which is not an error. The fruit cell in the middle of the notebook has pipeline.fit(X, y) commented out at the end. That is fine for reading a cross-validation score — cross_val_score clones the pipeline internally and never touches your object — but it means the pipeline variable is still unfitted afterwards. Call fit on all the data before you try to predict with it, or use grid.best_estimator_, which is already refitted.
APPENDIX A2 · Reference
Naming in a param grid
Where the double underscore comes from, and what to type when you are nested

A grid search addresses a parameter by path: the name of the step, then a double underscore, then the parameter. The double underscore is a separator, not a convention you can vary — svm_C and svm.C are both errors.

step name + __ + parameter name
you wrotethe key to usewhy
KNeighborsClassifier() alone'n_neighbors'No pipeline, no prefix.
Pipeline([('knn', KNN())])'knn__n_neighbors'The name you chose for the step.
make_pipeline(MinMaxScaler(), KNN())'kneighborsclassifier__n_neighbors'Auto-named: the class name, lowercased.
Pipeline([('prep', ColumnTransformer([('cat', OneHotEncoder(), …)]))])'prep__cat__handle_unknown'Nesting chains: one __ per level.
swapping the step itself'scaler': [MinMaxScaler(), StandardScaler()]A step name with no __ replaces the whole step.
🧭 When in doubt, ask the object. pipeline.get_params().keys() prints every legal key for that exact pipeline, nesting and all. It is faster than guessing, and it is the first thing to run when a search dies with ValueError: Invalid parameter 'knn' for estimator Pipeline(...).

Two shapes worth keeping, because they cover most of what you will ever need:

python — searching a step, and searching for the step
# 1. a list of dicts: search different kernels with different parameters
param_grid = [
    {'svm__kernel': ['linear'], 'svm__C': [0.1, 1, 10]},
    {'svm__kernel': ['rbf'],    'svm__C': [0.1, 1, 10],
     'svm__gamma': [0.01, 0.1, 1]}
]
# 3 + 9 = 12 combinations instead of 3 x 3 x 3 = 27,
# because gamma is meaningless for a linear kernel

# 2. let the search choose the preprocessing as well
param_grid = {
    'scaler': [MinMaxScaler(), StandardScaler(), 'passthrough'],
    'knn__n_neighbors': [1, 3, 5]
}
# 'passthrough' means "skip this step entirely" — so the search
# also answers the question "does scaling help at all here?"
⏱ And when the grid gets too big. RandomizedSearchCV takes the same estimator and the same kind of dictionary, but samples n_iter combinations at random instead of trying all of them — and accepts distributions such as scipy.stats.loguniform(1e-3, 1e3) in place of lists. With more than a few hundred combinations it reliably finds something nearly as good in a fraction of the time, because most hyper-parameters do not matter and a random search does not waste its budget proving that one by one.
